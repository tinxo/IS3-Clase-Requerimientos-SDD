Título: ADR-002 - Selección de Django como framework backend
Estado: Aceptado
Fecha: 2026-04-28
Decisores: Equipo de arquitectura
Relacionado: project.md (sección 3.1 Backend), contracts.md

Contexto
- El sistema de recepción de pacientes en emergencias requiere un framework web robusto y maduro para el backend
- Se necesita un ORM potente para manejar relaciones complejas entre Paciente, Visita, Triage, Atención, Diagnósticos, etc.
- El equipo requiere alta productividad para completar el MVP en 6-8 semanas
- Se requiere un panel de administración funcional desde el inicio para configuración de datos maestros (coberturas, usuarios, etc.)
- El sistema debe cumplir con requisitos estrictos de seguridad y auditoría según Ley 25.326 (datos sensibles de salud)
- El volumen de tráfico es moderado (< 50 pacientes/día, 5-15 usuarios concurrentes), no se requiere ultra-alta performance
- El sistema es crítico para operación 24/7 del servicio de emergencias

Decisión
- Se utiliza Django 5.x como framework backend principal del sistema
- Python 3.12+ como lenguaje de programación
- Django REST Framework 3.15+ para las APIs REST
- Django admin como base para interfaces administrativas
- Django ORM para todas las operaciones de base de datos
- No se utilizará GraphQL ni otros paradigmas de API en el MVP

Alcance:
- Aplica a todos los módulos del sistema (core, pacientes, triage, atención, dashboard, reportes)
- Django Templates se utilizará para renderizado server-side con HTMX para interactividad (ver ADR-004)
- El stack incluye librerías del ecosistema Django: django-auditlog, django-guardian, django-crispy-forms

Alternativas consideradas
- Opción A: FastAPI - Descartado por:
  * No incluye sistema de administración integrado (requeriría desarrollo custom significativo)
  * Mayor complejidad inicial para CRUD completo
  * Menor ecosistema de librerías para autenticación/autorización/auditoría
  * Aunque más rápido, la performance no es el cuello de botella del proyecto
  
- Opción B: Flask - Descartado por:
  * Requiere mucho más trabajo de configuración inicial (ORM, migraciones, admin, permisos)
  * No tiene ORM integrado (requeriría SQLAlchemy)
  * Timeline de 6-8 semanas muy ajustado para desarrollo desde cero
  
- Opción C: Django (seleccionado) - Elegido por:
  * Admin panel integrado y funcional out-of-the-box
  * ORM maduro con soporte completo para PostgreSQL incluyendo tipos JSON
  * Ecosistema extenso de paquetes para seguridad, auditoría y permisos
  * Sistema de migraciones robusto y probado
  * Documentación extensa y comunidad activa
  * Equipo tiene experiencia previa con Django

Consecuencias

Beneficios esperados:
- Desarrollo rápido del MVP gracias a "batteries included" de Django
- Admin panel permite configurar datos maestros sin desarrollar UI custom
- ORM reduce significativamente código SQL manual y previene inyección SQL
- Sistema de permisos granular (django-guardian) facilita implementación de roles
- django-auditlog permite cumplir requisitos de Ley 25.326 con configuración mínima
- Sistema de templates y formularios acelera desarrollo de vistas CRUD
- Migraciones facilitan evolución del schema a medida que crece el sistema

Costos o riesgos aceptados:
- Django es un framework "opinionated": el equipo debe seguir convenciones Django (MTV pattern, configuración en settings.py, etc.)
- Performance levemente inferior a FastAPI en benchmarks sintéticos, pero irrelevante para el volumen del proyecto
- El ORM puede generar queries subóptimas en casos complejos (mitigable con select_related/prefetch_related y raw SQL cuando necesario)
- Actualizaciones de versión de Django requieren testing de compatibilidad con librerías de terceros
- Curva de aprendizaje para desarrolladores no familiarizados con Django (mitigado por experiencia del equipo)

Impacto en operación y equipo:
- Equipo debe familiarizarse con convenciones de Django (signals, middleware, managers, querysets)
- Despliegue requiere servidor WSGI (Gunicorn) detrás de reverse proxy (Nginx)
- Monitoreo debe adaptarse a aplicaciones Django (django-prometheus, Sentry para errores)

Plan de implementación

Pasos mínimos:
1. Crear proyecto Django con estructura modular (apps/core, apps/pacientes, etc.)
2. Configurar settings por ambiente (base, development, production)
3. Instalar y configurar django-auditlog, django-guardian, DRF
4. Definir modelos según contracts.md
5. Generar migraciones iniciales
6. Configurar Django admin para modelos principales
7. Implementar autenticación y sistema de roles en apps/core

Dependencias:
- PostgreSQL 16 debe estar instalado y configurado (ver ADR-001)
- Variables de entorno definidas (.env con SECRET_KEY, DB_*, etc.)
- Python 3.12+ y pip instalados en ambiente de desarrollo y producción

Métrica de éxito:
- Módulo core con autenticación funcional en Semana 1
- CRUD de pacientes operativo en Semana 2
- Panel de admin permite gestionar usuarios y coberturas sin código custom
- Tests de integración pasan con cobertura > 80%

Triggers de revisión

Condiciones que obligarían a reabrir esta ADR:
- Performance del ORM se convierte en cuello de botella (tiempos de respuesta > 2 segundos sostenidos)
- Volumen de pacientes crece a > 500 pacientes/día y el sistema no escala
- Aparecen limitaciones críticas de Django para algún requerimiento futuro (ej: GraphQL subscriptions en tiempo real)
- Equipo técnico cambia y no tiene experiencia con Django (requerirían re-training significativo)

Fecha sugerida de revisión:
- Post-MVP (fin de Semana 8) - Evaluar si las ventajas de productividad se cumplieron
- 6 meses post-lanzamiento - Evaluar performance real bajo carga operativa
