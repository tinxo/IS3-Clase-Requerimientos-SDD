Título: ADR-005 - Despliegue on-premise en servidores propios
Estado: Aceptado
Fecha: 2026-04-28
Decisores: Equipo de arquitectura, Dirección del hospital
Relacionado: project.md (sección 2.2 Restricciones Técnicas, sección 6 Infraestructura)

Contexto
- El sistema maneja datos sensibles de salud protegidos por Ley 25.326 de Argentina
- El hospital cuenta con infraestructura de servidores propios y equipo de IT para gestión on-premise
- Volumen de pacientes es moderado (< 50 pacientes/día, 5-15 usuarios concurrentes)
- El sistema es crítico para operación 24/7 del servicio de emergencias
- Downtime inaceptable durante horario de operación (disponibilidad objetivo > 99.5%)
- RPO establecido en 24 horas (pérdida de datos aceptable)
- Costos operativos del hospital son limitados (presupuesto ajustado para soluciones cloud)
- Regulaciones de salud argentinas requieren control estricto sobre dónde residen los datos
- El hospital tiene políticas restrictivas sobre datos médicos en infraestructura de terceros
- Latencia de red a servicios cloud externos puede ser variable (hospital en zona con conectividad limitada)

Decisión
- El sistema se despliega on-premise en servidores físicos o virtuales dentro del datacenter del hospital
- Stack de producción:
  * Nginx como reverse proxy y terminación SSL (TLS 1.3)
  * Gunicorn como servidor WSGI (4-8 workers)
  * Django application
  * PostgreSQL 16 en el mismo servidor o servidor de BD dedicado
  * Servidor de backup dedicado en red local del hospital
  
- Configuración de servidores:
  * Servidor principal: Ubuntu 22.04/24.04 LTS
  * Mínimo: 4 cores CPU, 8GB RAM, 100GB SSD
  * Recomendado: 8 cores CPU, 16GB RAM, 250GB SSD
  
- Estrategia de backup on-premise:
  * Backups diarios completos (02:00 AM) con retención de 30 días
  * Backups incrementales cada 6 horas con retención de 7 días
  * Almacenamiento en servidor de backup dedicado en misma red local
  * Encriptación AES-256 de todos los backups
  
Alcance:
- Aplica a todos los ambientes de producción del MVP
- Ambientes de desarrollo y staging pueden ser locales (laptops de desarrolladores)
- No se utiliza cloud público (AWS, Azure, GCP) para ningún componente crítico
- Monitoreo puede usar servicios externos SaaS (Sentry, UptimeRobot) solo para alertas (no almacenan datos sensibles)

Alternativas consideradas
- Opción A: Cloud público (AWS/Azure/GCP) - Descartado por:
  * Preocupaciones legales y de compliance con Ley 25.326 (datos en servidores extranjeros)
  * Políticas del hospital prohíben datos de pacientes en infraestructura de terceros
  * Costos mensuales recurrentes (EC2, RDS, S3, etc.) superan presupuesto disponible
  * Dependencia de conectividad a internet (riesgo de downtime si ISP falla)
  * Latencia adicional para cada request (roundtrip a datacenter externo)
  * Requiere expertise en cloud que equipo de IT del hospital no posee
  
- Opción B: Híbrido (app en cloud, BD on-premise) - Descartado por:
  * Complejidad de conectividad segura (VPN, Direct Connect)
  * Latencia entre app y BD degrada performance
  * No resuelve preocupaciones de compliance (datos de pacientes transitan por cloud)
  * Mayor superficie de ataque (más componentes expuestos)
  
- Opción C: On-premise (seleccionado) - Elegido por:
  * Control total sobre datos sensibles (cumplen completamente con Ley 25.326)
  * No hay costos recurrentes de cloud (solo hardware inicial y electricidad)
  * Latencia mínima (servidor en red local del hospital)
  * No depende de conectividad a internet para operación crítica
  * Equipo de IT del hospital tiene experiencia gestionando servidores on-premise
  * Backups permanecen en infraestructura controlada por el hospital

Consecuencias

Beneficios esperados:
- Compliance completo con Ley 25.326: datos nunca salen de infraestructura del hospital
- Latencia mínima: red local (< 5ms) vs internet (50-200ms a cloud)
- Sin dependencia de internet: sistema funciona aunque ISP falle
- Costos predecibles: solo hardware inicial, electricidad, y mantenimiento
- Control total: equipo de IT puede acceder físicamente a servidores si es necesario
- Privacidad máxima: no hay terceros con acceso potencial a datos

Costos o riesgos aceptados:
- Escalamiento vertical limitado: si volumen de pacientes crece, requiere comprar/agregar hardware
- Responsabilidad de gestión: equipo de IT debe monitorear, mantener, y actualizar servidores
- Sin alta disponibilidad automática: no hay auto-scaling, load balancers gestionados, o multi-AZ como en cloud
- Backups limitados a infraestructura local: disaster recovery geográfico (ej: incendio en datacenter) es más complejo
- Actualizaciones de seguridad: equipo debe aplicar patches de SO y software manualmente
- Requiere UPS y generador: para garantizar uptime 24/7 ante cortes de energía
- No se aprovechan servicios gestionados de cloud (RDS, ElastiCache, CloudWatch, etc.)

Impacto en operación y equipo:
- Equipo de IT del hospital asume responsabilidad de:
  * Instalación y configuración inicial de servidores
  * Monitoreo 24/7 de disponibilidad y performance
  * Aplicación de actualizaciones de seguridad (SO, PostgreSQL, Python, Django)
  * Gestión de backups (verificar que se ejecuten, pruebas de restore mensuales)
  * Respuesta a incidentes (reiniciar servicios, investigar errores)
  
- Equipo de desarrollo debe:
  * Documentar procedimientos de deploy claramente
  * Proveer scripts de deploy automatizado (evitar deploy manual)
  * Capacitar a equipo de IT en troubleshooting básico de Django
  * Configurar alertas apropiadas (Sentry para errores, Prometheus para métricas)

Plan de implementación

Pasos mínimos:
1. Provisionar servidor con Ubuntu 22.04/24.04 LTS (8 cores, 16GB RAM, 250GB SSD recomendado)
2. Instalar dependencias:
   - Python 3.12+
   - PostgreSQL 16
   - Nginx
   - Supervisor o systemd para gestionar Gunicorn
3. Configurar PostgreSQL:
   - Crear base de datos emergencias_db
   - Configurar usuario con permisos apropiados
   - Habilitar backups automáticos con pg_dump
4. Configurar Nginx:
   - Reverse proxy a Gunicorn en puerto 8000
   - Configurar SSL con certificado (Let's Encrypt o certificado interno del hospital)
   - Servir archivos estáticos (/static/) y media (/media/)
5. Configurar Gunicorn:
   - 4-8 workers (2 x cores de CPU)
   - Timeout de 30 segundos
   - Logging a archivo para debugging
6. Deploy de aplicación Django:
   - Clonar repositorio o copiar código
   - Instalar dependencias de requirements/production.txt
   - Ejecutar migraciones: python manage.py migrate
   - Collectstatic: python manage.py collectstatic
   - Reiniciar Gunicorn
7. Configurar backups:
   - Cron job para pg_dump diario a las 02:00 AM
   - Script de backup incremental cada 6 horas
   - Encriptación con GPG antes de mover a servidor de backup
8. Configurar monitoreo:
   - Instalar agente Prometheus o configurar django-prometheus
   - Configurar Sentry para captura de errores
   - Configurar UptimeRobot para monitoreo de disponibilidad externo

Dependencias:
- Servidores físicos o VMs provisionados por equipo de IT
- Red local del hospital con IPs estáticas asignadas
- Firewall configurado para permitir tráfico HTTPS (puerto 443) a servidor
- Certificado SSL (Let's Encrypt o CA interna del hospital)
- Servidor de backup dedicado con espacio suficiente (mínimo 500GB para 30 días de retención)

Métrica de éxito:
- Sistema accesible 24/7 desde red local del hospital
- Latencia de requests < 500ms (objetivo < 200ms)
- Uptime > 99.5% mensual
- Backups se ejecutan exitosamente y pruebas de restore pasan
- Equipo de IT puede hacer deploy de nuevas versiones sin asistencia de desarrolladores

Triggers de revisión

Condiciones que obligarían a reabrir esta ADR:
- Volumen de pacientes crece significativamente (> 500/día) y servidor on-premise no escala
- Hospital abre múltiples sucursales y requiere acceso remoto desde otras ubicaciones
- Regulaciones cambian permitiendo datos en cloud con proveedores certificados
- Disaster recovery geográfico se vuelve requisito (necesita datacenter secundario)
- Equipo de IT del hospital se reduce y no puede gestionar infraestructura on-premise
- Costos de electricidad y mantenimiento de hardware superan costos de cloud
- Auditorías revelan problemas de seguridad o compliance que cloud resolvería mejor

Fecha sugerida de revisión:
- Post-MVP (fin de Semana 8) - Evaluar si deploy on-premise fue exitoso
- 6 meses post-lanzamiento - Evaluar performance, uptime, y carga operativa del equipo de IT
- Anualmente - Revisar costos totales (hardware, electricidad, personal) vs costos proyectados de cloud
