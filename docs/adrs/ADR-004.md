Título: ADR-004 - Enfoque híbrido frontend (Django Templates + HTMX + Alpine.js)
Estado: Aceptado
Fecha: 2026-04-28
Decisores: Equipo de arquitectura
Relacionado: project.md (sección 3.2 Frontend Web), ADR-002, ADR-003

Contexto
- El sistema requiere interfaces web para 5-15 usuarios concurrentes (recepcionistas, enfermeros, médicos)
- Timeline de MVP es ajustado (6-8 semanas) y el equipo debe priorizar funcionalidad sobre experiencia de usuario avanzada
- Se necesita interactividad moderada: actualización de listas, formularios dinámicos, validación en tiempo real
- Los usuarios operan bajo presión en servicio de emergencias, requieren interfaces rápidas y confiables
- No se requiere estado complejo del lado del cliente (no es una SPA colaborativa tipo Google Docs)
- El equipo tiene experiencia en Django pero experiencia limitada en frameworks frontend modernos (React, Vue, Angular)
- Se espera desarrollar app móvil React Native en Fase 2, pero el MVP es solo web
- El sistema debe funcionar en navegadores modernos (Chrome, Firefox, Edge) sin requisitos de compatibilidad con IE11

Decisión
- Se utiliza un enfoque híbrido para el frontend web:
  * **Django Templates** como base para renderizado server-side (SSR)
  * **HTMX** para interactividad sin JavaScript pesado (actualización parcial de página, AJAX declarativo)
  * **Alpine.js** para reactividad ligera en componentes específicos (dropdowns, modales, tabs)
  * **Bootstrap 5** como framework CSS para diseño responsive
  * **django-crispy-forms + crispy-bootstrap5** para renderizado elegante de formularios

Alcance:
- Aplica a todas las interfaces web del MVP (no a la app móvil de Fase 2)
- Django templates se usan para todas las páginas (base.html, pacientes/, triage/, atencion/, etc.)
- HTMX se utiliza para:
  * Búsqueda de pacientes con resultados en tiempo real
  * Actualización de dashboard de espera sin recargar página
  * Envío de formularios con validación inline
  * Carga de detalles de paciente en modales
- Alpine.js se limita a:
  * Interacciones UI simples (mostrar/ocultar, tabs, acordeones)
  * Formularios con campos condicionales (ej: si nivel ESI = 1, mostrar campos adicionales)
  * Validación básica del lado del cliente antes de submit

No se utiliza en el MVP:
- Frameworks SPA (React, Vue, Angular, Svelte)
- WebSockets para tiempo real (se agregará en Fase 2 con Django Channels)
- Estado complejo del lado del cliente (Redux, Vuex, Pinia)

Alternativas consideradas
- Opción A: SPA con React + API REST - Descartado por:
  * Timeline de 6-8 semanas insuficiente para desarrollar frontend completo en React
  * Equipo requeriría capacitación en React (useState, useEffect, routing, state management)
  * Complejidad adicional de configurar build process (Webpack/Vite), bundling, transpiling
  * Duplicación de lógica (validaciones en frontend y backend)
  * SEO y accesibilidad requieren SSR (Next.js), agregando más complejidad
  * Overhead de gestionar dos proyectos separados (backend Django + frontend React)
  
- Opción B: Django Templates puro sin HTMX/Alpine - Descartado por:
  * Experiencia de usuario muy básica (cada acción recarga página completa)
  * Búsqueda de pacientes requeriría submit de formulario y página nueva
  * Dashboard de espera no se actualizaría sin refresh manual
  * Pérdida de estado en formularios al navegar
  * Percepción de sistema "anticuado" por usuarios
  
- Opción C: Enfoque híbrido Django + HTMX + Alpine (seleccionado) - Elegido por:
  * Máxima productividad: Django templates + crispy-forms = formularios automáticos
  * HTMX permite AJAX sin escribir JavaScript (hx-get, hx-post, hx-target en HTML)
  * Alpine.js es minimalista (15kb) y sintaxis similar a Vue (x-data, x-show, x-if)
  * No requiere build process ni transpiling (se carga desde CDN)
  * SSR por defecto = mejor performance inicial y SEO
  * Menor curva de aprendizaje para equipo con experiencia Django
  * Interactividad suficiente para las necesidades del proyecto

Consecuencias

Beneficios esperados:
- Desarrollo rápido: Django templates + crispy-forms generan formularios completos con validación
- Performance: SSR reduce tiempo de carga inicial vs SPA
- Simplicidad: No hay build process, bundling, ni transpiling (menos tooling)
- HTMX permite actualizar partes de página sin JavaScript custom (declarativo)
- Alpine.js cubre casos de interactividad simple sin framework pesado
- Bootstrap 5 provee componentes UI listos (modales, alerts, cards, forms)
- Menor separación frontend/backend: mismos templates de Django sirven HTML directamente
- Debugging más simple: View-source muestra HTML real, no JS generado

Costos o riesgos aceptados:
- Interactividad limitada comparada con SPA (no ideal para experiencias tipo dashboard en tiempo real)
- HTMX es menos conocido que React/Vue (menor comunidad, menos recursos de aprendizaje)
- Estado del cliente limitado (Alpine.js no es Redux, no hay store global sofisticado)
- Transición futura a React Native (Fase 2) no reutiliza código web (no hay componentes React compartidos)
- Testing de UI más manual (no hay herramientas como React Testing Library / Cypress especializado en HTMX)
- Actualizaciones en tiempo real limitadas sin WebSockets (polling con HTMX es posible pero menos eficiente)

Impacto en operación y equipo:
- Equipo debe aprender HTMX (sintaxis hx-get, hx-post, hx-swap, hx-trigger)
- Alpine.js tiene sintaxis similar a Vue (x-data, x-show, x-if) - curva de aprendizaje baja
- Debugging requiere inspeccionar requests AJAX en DevTools (no hay React DevTools)
- Performance se monitorea en servidor (tiempos de respuesta Django) vs métricas de cliente (FCP, TTI)

Plan de implementación

Pasos mínimos:
1. Crear base.html con estructura HTML5, Bootstrap 5, HTMX y Alpine.js desde CDN:
   ```html
   <script src="https://unpkg.com/htmx.org@1.9.10"></script>
   <script src="https://unpkg.com/alpinejs@3.x.x/dist/cdn.min.js"></script>
   <link href="https://cdn.jsdelivr.net/npm/bootstrap@5.3.0/dist/css/bootstrap.min.css">
   ```
2. Configurar django-crispy-forms con crispy-bootstrap5 en settings.py
3. Crear componentes reutilizables en templates/components/:
   - form_field.html (campo de formulario con validación)
   - modal.html (modal Bootstrap con HTMX)
   - search_box.html (búsqueda con HTMX)
4. Implementar vistas Django que respondan HTML parcial para HTMX (ej: buscar_pacientes retorna solo <tr> de tabla)
5. Agregar hx-get/hx-post en formularios y botones donde se necesite interactividad
6. Usar Alpine.js para componentes con estado local (tabs, mostrar/ocultar campos condicionales)

Dependencias:
- Django configurado (ADR-002)
- Bootstrap 5 para estilos
- Navegadores modernos en estaciones de trabajo del hospital

Métrica de éxito:
- Búsqueda de pacientes muestra resultados sin recargar página (HTMX)
- Dashboard de espera se actualiza cada 30 segundos automáticamente (HTMX polling)
- Formularios de triage con campos condicionales funcionan sin recargar (Alpine.js)
- Tiempo de carga de páginas < 1 segundo
- Usuarios pueden completar flujo completo (registrar paciente -> triage -> atención) sin problemas de UX

Triggers de revisión

Condiciones que obligarían a reabrir esta ADR:
- Usuarios reportan experiencia de usuario insuficiente o confusa
- Se requiere dashboard en tiempo real sofisticado (gráficos interactivos, drag-and-drop) que HTMX/Alpine no puede soportar
- Equipo crece y se incorporan desarrolladores con fuerte experiencia React que prefieren SPA
- Fase 2 requiere reutilización de componentes entre web y móvil (favore cerí a React web + React Native)
- Performance de SSR se vuelve cuello de botella (tiempos de respuesta > 2 segundos)

Fecha sugerida de revisión:
- Post-MVP (fin de Semana 8) - Recolectar feedback de usuarios sobre experiencia de uso
- 6 meses post-lanzamiento - Evaluar si limitaciones de HTMX/Alpine impactan operación diaria
