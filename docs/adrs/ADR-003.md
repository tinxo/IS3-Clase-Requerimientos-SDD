Título: ADR-003 - Arquitectura modular del sistema (6 módulos Django)
Estado: Aceptado
Fecha: 2026-04-28
Decisores: Equipo de arquitectura
Relacionado: project.md (sección 1.3 y 4.2), contracts.md, ADR-002

Contexto
- El sistema de emergencias cubre múltiples dominios: gestión de pacientes, triage, atención médica, reportes, etc.
- El equipo está desarrollando en un timeline ajustado de 6-8 semanas para el MVP
- Se espera que diferentes módulos evolucionen a diferente ritmo (ej: triage es estable, reportes puede crecer significativamente)
- Múltiples desarrolladores trabajarán en paralelo en diferentes áreas del sistema
- Se necesita separación clara de responsabilidades para facilitar testing y mantenimiento
- El sistema debe ser extensible para Fase 2 (app móvil React Native, integración HL7 FHIR)
- Django favorece el patrón de "apps" como unidad de modularización
- Se requiere reutilización de contratos compartidos (modelos, enums, validaciones) entre módulos

Decisión
- El sistema se estructura en 6 módulos Django (apps) independientes dentro de la carpeta apps/
- Cada módulo encapsula modelos, vistas, formularios, serializers, URLs y tests relacionados
- Se establece un módulo Core como base que provee infraestructura transversal
- Los contratos compartidos (modelos, enums, convenciones) se documentan centralmente en contracts.md
- Cada módulo tiene su propia especificación detallada en specs/

Los 6 módulos son:
1. **apps/core/** - Autenticación, autorización, auditoría, gestión de usuarios
2. **apps/pacientes/** - Registro maestro de pacientes, búsqueda, historial
3. **apps/triage/** - Clasificación ESI, visitas de emergencia, signos vitales
4. **apps/atencion/** - Atención médica, diagnósticos CIE-10, estudios, prescripciones
5. **apps/dashboard/** - Panel de monitoreo en tiempo real, lista de espera
6. **apps/reportes/** - Estadísticas, KPIs, exportación de datos

Reglas de dependencias entre módulos:
- Todos los módulos pueden depender de core (autenticación, permisos, auditoría)
- triage depende de pacientes (necesita modelo Paciente para VisitaEmergencia)
- atencion depende de triage (necesita VisitaEmergencia)
- dashboard y reportes pueden leer de todos los módulos pero no modificar datos
- pacientes NO debe depender de triage ni atencion (separación paciente permanente vs episodios)

Alcance:
- Aplica a toda la estructura del código backend
- Frontend (templates) también se organiza por módulo (templates/pacientes/, templates/triage/, etc.)
- Assets estáticos (JS, CSS) pueden compartirse o modularizarse según necesidad
- No aplica a Fase 2 (app móvil React Native es proyecto separado)

Alternativas consideradas
- Opción A: Monolito sin módulos (una sola app Django) - Descartado por:
  * Dificulta trabajo en paralelo del equipo (conflictos en models.py, views.py gigantes)
  * Testing más complejo (no se puede aislar fácilmente)
  * Menor claridad de responsabilidades (todo mezclado)
  * Más difícil de mantener a largo plazo
  
- Opción B: Microservicios independientes - Descartado por:
  * Excesiva complejidad para el alcance y volumen del proyecto
  * Requiere infraestructura adicional (API gateway, service discovery, orquestación)
  * Timeline de 6-8 semanas insuficiente para implementar comunicación entre servicios
  * Transacciones distribuidas complejas (ej: crear visita + triage en transacción atómica)
  * Overhead de despliegue y monitoreo de múltiples servicios
  
- Opción C: 6 módulos Django (seleccionado) - Elegido por:
  * Balance ideal entre modularidad y simplicidad para el alcance del proyecto
  * Patrón natural en Django (apps reutilizables)
  * Permite trabajo en paralelo sin complejidad de microservicios
  * Testing aislado por módulo pero con capacidad de tests de integración
  * Transacciones atómicas nativas de Django entre módulos
  * Facilita extensibilidad futura (agregar módulo de facturación, inventario, etc.)

Consecuencias

Beneficios esperados:
- Separación clara de responsabilidades: cada módulo tiene un propósito bien definido
- Trabajo en paralelo: 3 desarrolladores pueden trabajar en pacientes, triage y atención simultáneamente
- Testing más simple: tests unitarios por módulo, tests de integración entre módulos
- Reutilización: módulo core (autenticación, permisos) se reutiliza en todos los demás
- Escalabilidad del código: agregar funcionalidad nueva es agregar un módulo
- Documentación organizada: cada módulo tiene su spec (specs/core.md, specs/triage.md, etc.)
- Despliegue simplificado: un solo proyecto Django, una sola base de datos

Costos o riesgos aceptados:
- Coordinación necesaria para evitar dependencias circulares entre módulos
- Cambios en contratos compartidos (contracts.md) impactan múltiples módulos
- Overhead de imports entre módulos (ej: from apps.pacientes.models import Paciente)
- Migraciones deben gestionarse cuidadosamente cuando hay ForeignKeys entre módulos
- No se obtiene aislamiento completo de microservicios (todos los módulos comparten DB y runtime)

Impacto en operación y equipo:
- Equipo debe entender la arquitectura modular y respetar reglas de dependencias
- Code reviews deben verificar que no se violen dependencias (ej: pacientes importando de atencion)
- Documentación de contratos (contracts.md) se vuelve crítica y debe mantenerse actualizada
- Tests de integración deben cubrir interacciones entre módulos (ej: crear paciente -> iniciar visita -> hacer triage)

Plan de implementación

Pasos mínimos:
1. Crear estructura de carpetas según project.md sección 4.2:
   - emergencias/apps/core/
   - emergencias/apps/pacientes/
   - emergencias/apps/triage/
   - emergencias/apps/atencion/
   - emergencias/apps/dashboard/
   - emergencias/apps/reportes/
2. Configurar INSTALLED_APPS en settings.py con todos los módulos
3. Definir modelos de cada módulo según contracts.md
4. Establecer ForeignKeys respetando reglas de dependencia
5. Crear URLs principales en config/urls.py que incluyan URLs de cada módulo
6. Documentar specs individuales (specs/core.md, specs/pacientes.md, etc.)

Dependencias:
- Django configurado (ADR-002)
- contracts.md completo con modelos y convenciones
- Equipo alineado en reglas de dependencias entre módulos

Métrica de éxito:
- Cada módulo tiene tests que pasan independientemente
- No existen dependencias circulares entre módulos
- Tests de integración validan flujo completo: registro paciente -> triage -> atención
- Tiempo de desarrollo cumple con cronograma de 8 semanas
- Desarrolladores pueden trabajar en módulos diferentes sin conflictos de merge

Triggers de revisión

Condiciones que obligarían a reabrir esta ADR:
- Aparecen dependencias circulares irresolubles entre módulos
- Un módulo crece desproporcionadamente y requiere subdivisión (ej: atencion con > 20 modelos)
- Escalamiento real requiere separar módulos en microservicios independientes
- Performance se degrada por exceso de joins entre tablas de diferentes módulos
- Equipo crece significativamente (> 10 devs) y necesita mayor aislamiento

Fecha sugerida de revisión:
- Post-MVP (fin de Semana 8) - Evaluar si la modularización facilitó el desarrollo paralelo
- 1 año post-lanzamiento - Evaluar si algún módulo necesita subdivisión o extracción como microservicio
